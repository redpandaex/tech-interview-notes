## 主问题：Event Loop 与微任务

### 用户原始回答

> 1. A-G-D-F-B-C-E
> 2. 宏任务中可以执行同步代码和微任务,promise.then是微任务
> 3. 会导致浏览器卡顿吧,浏览器检测到有微任务时会不停的去执行这个微任务

**反馈：**
- 第 1 问完全正确：A → G → D → F → B → C → E。
- 第 2 问基本正确。更准确地说，先执行一个 Task 的同步代码，调用栈清空后执行微任务检查点，清空微任务队列。
- 第 3 问正确，属于 Microtask Starvation。微任务不断添加新微任务，会导致后续 Task 和渲染得不到机会。

## 第一次追问：分批处理与浏览器调度

### 用户原始回答

> 1. 方案B吧,方案A这个微任务会卡住浏览器好像
> 2. 有个叫做IDLE的好像是然后还有一个RAF应该也可以了

**反馈：**
- 选择 setTimeout 分批（B）正确。递归微任务可能让微任务检查点一直无法结束；分批安排到后续 Task 能让浏览器有机会处理其他工作。
- 记得 requestIdleCallback 和 requestAnimationFrame。前者适合非紧急空闲工作，后者适合重绘前视觉更新，不适合长时间计算。

## 第二次追问：100 万条数据排序

### 用户原始回答

> A或者C都可以吧'

**反馈：**
- A 在可切片、非紧急任务中可用，但计算仍然在主线程，必须控制每批执行时间，并正确设计排序与合并。
- C（Web Worker）更符合“不阻塞主线程”的强要求，因为 CPU 密集型排序在 Worker 线程执行。
- Worker 返回数据时要考虑 Structured Clone 的复制成本；可对适用数据使用 Transferable Objects。展示大量结果时还应使用虚拟列表。
