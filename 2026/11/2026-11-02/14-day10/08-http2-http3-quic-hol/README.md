# Day 10 · Q8 — HTTP/1.1、HTTP/2、HTTP/3 与队头阻塞

**评分：90/100**

## 题目

在线教育课程页同时加载 30 个 JavaScript、CSS、图片及接口资源。弱网丢包时，为什么 HTTP/2 已有多路复用却仍可能让多个资源一起等待？HTTP/3 如何改进？

回答：
1. HTTP/1.1 为什么出现队头阻塞，浏览器如何缓解？
2. HTTP/2 的 Stream、帧与 TCP 队头阻塞有什么关系？
3. HTTP/3 为什么使用基于 UDP 的 QUIC？如何避免跨流阻塞？

## 参考答案

### 一、HTTP/1.1：响应顺序与连接限制

HTTP/1.1 的 **Pipelining** 允许在同一连接上连续发送多个请求，而不必等前一个响应返回；但响应仍必须按请求顺序发送。若请求 A 的响应较慢，后续请求 B 即使已准备好也不能随意越过 A 返回。

```text
HTTP/1.1 Pipelining：同一 TCP 连接

请求： A ── B ── C ──────────>
响应： [ A 很慢 ] [ B ] [ C ]
                     ↑
            B 必须等待 A 的响应顺序
```

现代浏览器通常不启用 HTTP/1.1 Pipelining，常通过**同一来源建立多个 TCP 连接**并行请求来缓解等待：

```text
连接 1：请求 A ─────── 响应 A
连接 2：请求 B ── 响应 B
连接 3：请求 C ──── 响应 C
```

代价包括更多连接建立、资源开销，以及多个连接之间的竞争。

### 二、HTTP/2：应用层多路复用

HTTP/2 在一个 TCP 连接上承载多个逻辑 Stream。通常一个请求/响应交换对应一个 Stream，HEADERS、DATA 等帧携带 Stream ID，允许不同 Stream 的帧交错传输。

```text
HTTP/2：一个 TCP 连接

帧序列：
[A:HEADERS] [B:HEADERS] [A:DATA] [C:HEADERS] [B:DATA] ...
    │            │          │           │          │
    └─ Stream A ─┘          └─ Stream C └─ Stream B
```

HTTP/2 解决了 HTTP/1.1 在应用层按完整响应顺序等待的问题，但 **TCP 仍向上层提供单条可靠、有序字节流**。

若 TCP 中间一段字节丢失，后续 TCP 数据即使已到达接收端，也不能越过缺口按序交付给 HTTP/2。因为所有 HTTP/2 Stream 的帧都复用这一条 TCP 字节流，不同 Stream 可能一起等待。

```text
TCP 字节流：
[ A 数据 ] [ 丢失的 TCP 段 ] [ B 数据已到达 ]
                 ↑
           必须先恢复缺口
                 ↓
HTTP/2 暂时无法继续处理后面的 B 数据
```

因此：
- HTTP/2：**解决 HTTP 层的响应级队头阻塞**。
- HTTP/2 over TCP：**仍存在 TCP 传输层队头阻塞**。

### 三、HTTP/3：QUIC 的流级有序交付

HTTP/3 使用 QUIC。QUIC 运行在 UDP 之上，但自己实现可靠传输、丢包恢复、拥塞控制、流量控制、加密与多路复用。使用 UDP 不是为了放弃可靠性，而是为了在 TCP 之外实现不同的传输抽象。

QUIC 的不同 Stream 维护各自的数据偏移和有序交付状态。若 Stream A 的数据丢失，不要求 Stream B、C 等待 A 的缺口恢复才能交付各自完整连续的数据。

```text
QUIC 连接：
Stream A: [0..999] [缺口] [2000..2999 已缓存] → 后续数据交付等待缺口
Stream B: [0..999] [1000..1999]             → 可继续交付
Stream C: [0..999] [1000..1999]             → 可继续交付
```

**边界条件**：
- QUIC 不消除**同一个 Stream 内部**的有序交付等待。
- 一个丢失的 QUIC 数据包可能同时携带多个 Stream 的数据，导致多个流各自出现缺口。
- 不同流仍共享连接级拥塞控制、连接级流量控制及带宽、服务器资源；这些机制仍可能影响多个流的吞吐或延迟。
- 丢包后是否能继续交付，还取决于该流的数据是否完整连续、流量控制等条件。

### 四、追问：丢失的数据包包含 A、B 的数据，C 正常到达

**问题 1：C 是否能继续交付？**

可以。C 的数据只要完整连续且满足相关限制，不必等待 A、B 的缺失数据恢复。

**问题 2：A、B 是否完全不能接收？**

不是。应区分：
1. **接收数据包**：可以继续接收后续 QUIC 数据包。
2. **接收并缓存 Stream 数据**：可以缓存偏移量在缺口之后的数据。
3. **按序交付给应用层**：缺口之后的数据通常需等待丢失部分恢复。

```text
Stream A：
[ 0..999 已到达 ][ 1000..1999 丢失 ][ 2000..2999 已缓存 ]
         │                │                    │
   可以先交付        有序数据缺口          不能越过缺口按序交付
```

### 五、面试速记

| 协议 | 多路复用方式 | 主要队头阻塞特征 |
| --- | --- | --- |
| HTTP/1.1 | 无 HTTP/2 式帧级多路复用；可用多个 TCP 连接并行 | Pipelining 下响应必须按请求顺序返回 |
| HTTP/2 | 一个 TCP 连接上的多个 HTTP Stream | 消除 HTTP 响应级顺序阻塞，但 TCP 丢包可阻塞所有 Stream |
| HTTP/3 | QUIC 连接中的多个独立 Stream | 避免因单个 Stream 的丢包引发跨流有序交付阻塞；流内仍可阻塞 |

**一句话：** HTTP/2 的 Stream 独立于 HTTP 层，却共享 TCP 有序字节流；HTTP/3 的 QUIC 在传输层提供独立流的有序交付。
