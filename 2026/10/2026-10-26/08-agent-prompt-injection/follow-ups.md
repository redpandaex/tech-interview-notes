# Agent Prompt Injection 与工具调用安全 · 追问与答题记录

**状态：两轮追问已完成；最终评分 85/100**

## 用户原始回答（原文）

> 1. prompt注入攻击,agent可能忽视掉系统的提示词开始对主机进行操作
> 2. 不能,可能被prompt破壳
> 3. 我会不让这个agent去直接访问db,而是通过db工具来访问,同时在这个db工具中使用代码和当前使用者等context进行鉴权htpp工具也不能让他直接用,必须通过工具,最好在工具中采用白名单模式来使用

## 初步点评

1. **基本正确**：属于间接提示词注入（Indirect Prompt Injection）。恶意指令藏在上传 Word 文档这种不可信数据中，Agent 可能将数据错误提升为操作指令；风险具体取决于 SQL/HTTP 等工具权限，而非必然能控制主机。
2. **正确**：System Prompt 不构成强制访问控制边界。Jailbreak 与 Prompt Injection 有交集但并不完全相同，必须在模型外部的可信工具执行权限检查。
3. **回答较好**：DB 访问经受控工具；根据可信服务端认证上下文进行鉴权；HTTP 白名单。进一步应注意：
   - 不能让模型自行提供 `teacherId` 等身份并信任它；用户身份由服务端已验证会话注入。
   - 尽量提供 `getCourseScores(courseId)` 等业务工具，而不是任意 `querySql(sql)`；后端校验课程访问、使用参数化 SQL、最小权限账号、只读/限流/限时/限结果集。
   - HTTP 白名单需解析 URL 校验协议/主机名/端口/路径，防止前缀伪造、重定向、DNS/SSRF；更推荐最小权限的业务 HTTP 工具，而不是任意请求。
   - 若业务不需要通用 HTTP 工具，则不应开放。

## 第一轮追问（已答）

**场景 A：身份伪造**：模型调用 `getCourseScores({teacherId: 999, courseId: "C100"})`，但当前登录教师的真实 ID 是 `123`。如果 SQL 工具已经做了身份鉴权，如何防止模型利用传入的 `teacherId` 越权读取教师 999 的数据？

**场景 B：HTTP 白名单绕过**：工具只允许请求公司域名 `https://reports.example.com`，但模型尝试请求 `https://reports.example.com/collect?data=<学生成绩>`。域名是白名单内的，这样是否一定安全？应如何限制 HTTP 工具避免敏感数据外传？

## 第一轮追问：用户原始回答

> 1.查询工具应该从当前代码中检查用户id,不接受ai给的id
>
> 2. 不一定安全,但是他这样调用还是查不到的,除非接口本身就存在漏洞

### 点评

- 第 1 问正确：身份必须从可信的服务端上下文读取，而不是使用模型传入的 ID；还需校验当前教师是否有课程访问权。
- 第 2 问部分正确：HTTP 白名单不等于数据外发许可。模型可能把已经通过合法 SQL 查询得到的成绩发送给白名单域名内的接收接口，即使接口没有漏洞。应限制方法、路径、请求体、数据来源，并采用固定业务工具。

## 第二轮第 1 问：澄清后用户补充回答（原文）

> 从容器上限制不允许向外部发送请求之类的,或者限制白名单

### 最终点评

- **正确**：从容器/基础设施层限制网络出站请求（如 Kubernetes NetworkPolicy、网络防火墙、受控出口代理），默认禁止任意公网出口，只开放必需的内部服务。
- 网络白名单仍不能替代业务工具的权限校验：白名单内部服务也可能接收不该外发的数据；应限制操作、方法、路径、请求体和数据来源。
- 需在**实际发起请求的执行环境**实施网络策略：如果 Agent 调用远程 HTTP 工具服务，仅隔离 Agent 容器不能约束该远程工具的出口。
- 容器本身不自动意味着网络隔离，需明确网络策略和实际执行机制。
