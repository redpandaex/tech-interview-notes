# 浏览器 INP 与 Long Task 优化 · 追问与答题记录

**状态：两轮追问已完成；最终评分 80/100**

## 用户原始回答（原文）

> 因为浏览器的是单线程,js在处理的过程中渲染页面也会被卡住
> 应该可以

对应提问：
1. 用户点击后主线程执行 800ms 同步任务，为什么可能无法及时更新页面？
2. 把同步代码放进 `Promise.then()` 能不能解决页面卡顿？为什么？

## 面试官点评

- 第 1 问基本正确：页面 JavaScript 和大量渲染工作通常共享主线程，长时间执行同步 JS 会阻塞主线程；但不能笼统说“浏览器整体单线程”。
- 第 2 问不正确：`Promise.then` 是微任务，仍在主线程执行；微任务检查点通常先于浏览器获得下一次渲染机会。把 800ms 计算放进微任务不能自动分片或转移线程。
- 关键区分：异步调度 ≠ 多线程执行 ≠ 不阻塞主线程。
- 本题尚未完成，暂不做最终评分。

## 第一轮追问（已答）

```js
button.addEventListener("click", () => {
  document.querySelector("#status").textContent = "处理中...";

  setTimeout(() => {
    const start = performance.now();
    while (performance.now() - start < 800) {
      // 模拟耗时计算
    }
    document.querySelector("#status").textContent = "完成";
  }, 0);
});
```

1. `setTimeout(fn, 0)` 回调属于宏任务还是微任务？
2. 相比 `Promise.then()`，是否有可能先看到“处理中...”？
3. 是否能彻底解决 800ms 卡顿？为什么？



## 第一轮追问：用户原始回答

> 1. 宏任务
> 2. 没看懂这个
> 3. 不能吧

点评：第 1、3 题正确。第 2 题解释为：`setTimeout(fn, 0)` 安排后续任务，当前点击任务结束后浏览器**可能**有渲染机会，让“处理中...”先显示；但不保证下一次 timer 回调之前一定绘制。与之不同，`Promise.then` 是微任务，通常在渲染机会之前执行。无论哪种方式，单个 800ms 的同步任务仍会阻塞主线程。

## 第二轮追问（已答）

用户点击按钮后需要处理 100 万条数据，耗时 800ms，要求期间页面仍可响应交互。多选并解释：

- A. `Promise.then()` 包裹计算。
- B. `setTimeout(fn, 0)` 包裹整个计算。
- C. 分批计算，每批用 `setTimeout` 安排下一批。
- D. 使用 Web Worker 执行计算。

可补充比较 C 和 D。

## 第二轮追问：用户原始回答

> 哦哦哦,对哦,我在React中也是哟观察到这个,在commit阶段通过js改变了dom,但是dom不会立即去更新
> c或者d吧
> c的批量处理可以让用户没有感知,但是运行在主线程中
> d的话则是使用一个其他的线程去之星这个任务

## 最终点评

- **C、D 正确。** C 将 800ms 同步任务分片，每片仍运行在主线程，但片间让出主线程；D 使用 Web Worker 在工作线程执行 CPU 密集计算。
- C 不保证“完全无感”：每片过长仍会卡顿，且增加调度开销；按实际执行时长调整切片比固定数据条数更可靠。
- D 不能直接操作 DOM，数据传输可能有复制、序列化或 Transferable 管理成本。
- React Commit 阶段 DOM 已修改不等于浏览器已绘制，`useLayoutEffect` 的同步逻辑也可能阻塞绘制。
- 需要继续学习 INP 的输入延迟、处理耗时、呈现延迟三个部分，以及 DevTools Performance 分析。
- **最终评分：80/100。** 用户理解任务切片与工作线程的差别，初始对微任务与绘制时序有误，经过解释已能正确选型。
