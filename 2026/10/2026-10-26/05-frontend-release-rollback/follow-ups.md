## 用户原始回答（原文）

> 1. 可能是用户浏览器有缓存,导致页面没有被刷新,也有可能是CDN有缓存,导致该用户请求不到CDN的资源
> 2. js,css这类设置为尽可能大的max-age,但是index.html最好设置成no-cache或者no-store
> 3. 不删除旧页面的chunk,报酬并存

最后一项“报酬并存”按上下文理解为“保持并存”，但保留用户原文。

## 初步点评

1. **基本正确**：浏览器缓存、CDN 边缘缓存各自可能返回旧内容；资源 404 也可能来自上传/删除时序。还需区分“旧内容”和“资源无法访问”，以及已经打开的页面仍运行旧 JS 的情况。
2. **正确**：内容 Hash 的 JS/CSS 可设置 `Cache-Control: public, max-age=31536000, immutable`，前提是同名资源不可变；HTML 常用 `no-cache` 配合 ETag/304，`no-store` 更严格但减少复用。共享 CDN 缓存策略也要单独考虑。
3. **正确**：旧页面动态导入仍引用旧版 Chunk URL，应在部署后保留旧版静态资源，避免因删除文件而出现 `ChunkLoadError`；但无法单独保证 API 和微前端版本兼容。

### 原理示例

旧版 `main.aaa111.js` 动态引用 `SettingsPage.bbb222.js`；发布新版后若删除旧 Chunk，仍打开旧页面的用户点击设置时可能 404。新旧带 Hash 资源并存是必要的部署实践之一。

## 第一轮追问：用户原始回答

> 方案B,不然上传index.html如果静态资源访问不了,可能会导致一部分用户使用了这个新的html
> 不需要,只需要把v2的html资源删除就行了

### 点评

- **第一问完全正确**：先上传并验证带 Hash 的静态资源，再原子切换 HTML 入口，避免新 HTML 引用尚不存在的 JS/CSS。
- **第二问部分正确**：不删除 V2 静态资源是对的；但不应直接删除线上 HTML，否则可能产生 404。应将稳定入口 `/index.html` 或部署路由恢复至 V1 HTML，同时考虑 CDN 缓存更新。旧 V1、V2 资源应暂时共存，因为仍打开 V2 的用户可能继续懒加载 V2 Chunk。
- 回滚 HTML 不会自动替换已打开页面正在执行的 JS。



## 第二轮追问（已答）

V2 发布后回滚 V1，源站已经恢复 V1 HTML，但部分用户仍从 CDN 获取 V2 HTML：

1. 如何让这些用户尽快拿到 V1 HTML？
2. CDN 已返回 V1 HTML，仍打开 V2 页面的用户是否立即切换到 V1 JS？为什么？

### 用户原始回答

> 1. 强行清空v2资源的缓存.或者让nginx设置访问v2的资源时重定向到v1
> 2. 不会,因为v2的依赖依旧是v2的,不刷新的话检测不到

### 点评

- **第一问部分正确**：可通过 CDN 主动失效或刷新 HTML 入口（如 `/`、`/index.html`）的缓存，让 CDN 重新从已恢复 V1 的源站获取 HTML。应避免清空或删除 V2 的带 Hash 静态资源；仍打开 V2 的用户可能继续加载其旧 Chunk。缓存刷新也可能存在传播延迟。
- Nginx 可以切换 HTML 入口到 V1；但不能把 `main.v2.js` 简单重定向到 `main.v1.js`，否则可能造成模块不兼容、完整性校验失败等问题。
- **第二问正确**：已运行在浏览器中的 V2 JS 不会因源站/CDN 回滚自动替换；需刷新或由应用检测版本变化后受控刷新，注意未保存表单及刷新循环。
