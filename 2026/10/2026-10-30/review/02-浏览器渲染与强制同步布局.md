# 专题二：浏览器渲染、重排重绘与强制同步布局

> 第 6 天面试复习 · 对应第 8 题（62/100）  
> 学习目标：能把浏览器渲染阶段与 Event Loop、强制同步布局和实际性能优化联系起来。

## 1. 从 HTML 到像素：简化渲染流水线

```text
HTML → DOM ──────────┐
                     ├→ 样式计算 → 布局结构 → Layout → Paint → Composite → 屏幕
CSS  → CSSOM ────────┘
```

- **DOM**：描述文档节点及层级。
- **CSSOM**：解析后的 CSS 规则模型；浏览器结合层叠、继承等计算样式。
- **Render Tree**：教学中的简化概念，表示参与渲染的可视结构；现代浏览器内部会使用更细分的布局树、绘制记录、合成层等结构。
- **Layout（布局/重排）**：计算布局盒的大小、位置、文本换行等几何信息。
- **Paint（绘制）**：生成背景、文字、边框、阴影等绘制指令。
- **Composite（合成）**：将不同层的内容按变换、透明度等信息组合到屏幕。

`display: none` 的元素不生成布局盒；`visibility: hidden` 通常仍占据布局空间；伪元素可能生成布局盒。**DOM 不是布局树的简单一对一复制。**

## 2. 哪些属性影响哪些阶段？

| 修改 | Layout | Paint | Composite | 典型原因 |
|---|---|---|---|---|
| `width` | 通常需要 | 通常需要 | 可能需要 | 几何尺寸变化 |
| `margin` / `top` / `left` | 通常需要 | 可能需要 | 可能需要 | 布局或位置变化 |
| `background-color` | 通常不需要 | 通常需要 | 可能需要 | 可见外观变化 |
| `transform` | 通常不需要 | 可能跳过 | 通常需要 | 变换可由合成处理 |
| `opacity` | 通常不需要 | 可能跳过 | 通常需要 | 透明度可由合成处理 |

**注意：** 这是常见路径，不是浏览器必须执行的固定序列。

### Layout 一定导致 Paint 吗？

不一定。布局工作可能只影响不可见区域，或者已有绘制结果能够复用。即使布局计算执行了，也不意味着必须重新绘制全部内容。

### Paint 一定导致 Composite 吗？

最终显示内容需要被呈现，但 Paint 不意味着必须立刻进行一次独立且完整的 Composite；浏览器可以合并、跳过或复用工作。

### 为什么 transform 动画通常比 left 好？

`left` 影响定位布局，通常导致布局计算；`transform: translateX()` 通常不改变正常文档流中的占位，在适合的合成条件下可以直接更新变换。**并不保证所有 transform 修改都只触发合成**。过多合成层也可能增加内存开销。

## 3. 样式写入通常是延迟批量处理的

```js
box.style.width = '300px';
box.style.height = '400px';
box.style.marginLeft = '20px';
```

浏览器一般可以先标记布局信息失效，等到适当的渲染时机再统一计算，而不是每行都立即 Layout。

## 4. 什么是强制同步布局（Forced Synchronous Layout）？

```js
box.style.width = '300px'; // 写入：布局信息可能过期
console.log(box.offsetWidth); // 读取：要求最新几何结果
box.style.height = '400px'; // 再写入
```

如果读取 `offsetWidth` 时布局信息已经失效，浏览器为了返回准确尺寸，**可能被迫提前同步执行样式计算与布局**。

常见布局读取 API：

- `offsetWidth`、`offsetHeight`、`offsetTop`
- `clientWidth`、`clientHeight`
- `scrollWidth`、`scrollHeight`（具体是否强制计算取决于状态）
- `getBoundingClientRect()`

`getComputedStyle()` 是**读取计算样式**，不是修改样式；它可能强制样式计算，在某些条件下读取特定属性也可能强制布局，不能把它当作优化替代品。

## 5. Layout Thrashing：循环里反复读写

反例：

```js
const boxes = document.querySelectorAll('.box');
for (const box of boxes) {
  box.style.width = '300px'; // 写
  console.log(box.offsetWidth); // 读：可能强制 Layout
}
```

反复「写→读→写→读」可能造成大量重复布局计算，这叫 **Layout Thrashing（布局抖动）**。

改进：**读写分离**。

```js
const boxes = [...document.querySelectorAll('.box')];

// 第一阶段：集中读取
const widths = boxes.map(box => box.offsetWidth);

// 第二阶段：集中写入
boxes.forEach((box, index) => {
  box.style.width = `${widths[index] + 10}px`;
});
```

还可以：

1. 优先使用 CSS 布局能力而非 JS 逐项计算。
2. 动画优先考虑 `transform` / `opacity`，并测量真实效果。
3. 使用 `requestAnimationFrame` 与浏览器绘制节奏协调，但它**不会自动消除读写交替**。
4. 避免为每帧创建过多独立合成层；谨慎使用 `will-change`。

## 6. 和 Event Loop 放在一起理解

```text
选择一个 Task（常口语称宏任务）
    ↓
执行同步 JS（可能修改样式）
    ↓
执行微任务检查点，直到微任务队列清空
    ↓
浏览器可能进行渲染更新（并非每轮必定）
    ↓
后续任务
```

```js
box.style.width = '100px';
Promise.resolve().then(() => { box.style.width = '200px'; });
queueMicrotask(() => { box.style.width = '300px'; });
```

浏览器通常可以合并这些变化，而不必把 100px、200px、300px 逐帧显示出来。**渲染不是每个任务结束后必然发生**；连续产生微任务还可能导致渲染饥饿。

`requestAnimationFrame()` 的回调通常在浏览器准备进行渲染更新时执行，并不是普通的 `setTimeout` 宏任务。

## 7. DevTools 如何验证？

1. 打开 Performance 面板录制一次滚动/交互。
2. 找到 Main 线程上的 `Recalculate Style`、`Layout`、`Paint` 等事件。
3. 检查是否存在 Forced Reflow 提示、长任务、频繁布局。
4. 对比优化前后帧耗时和用户可感知指标，而不是只凭属性名称判断性能。

## 8. 面试速答（90 秒）

> 浏览器解析 HTML/CSS 形成 DOM/CSSOM，进行样式计算，随后 Layout 计算几何信息，Paint 生成绘制指令，Composite 合成结果。width 通常触发布局，background-color 通常只需绘制，transform 在合成优化条件下可能只需合成。浏览器通常批量处理样式变化，但如果写入影响布局的样式后立即读取 offsetWidth，可能强制同步布局。循环中反复读写会形成布局抖动，优化方式是集中读取、集中写入，并用 Performance 面板验证。
